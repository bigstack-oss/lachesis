# Implementation Contracts & Deferred Work

The design leaves a few load-bearing properties to the implementation. This
chapter lists them explicitly so they don't get lost between spec and code —
first the contracts any build must satisfy, then the work that is out of scope
*by decision*, with its retrofit path.

## Required contracts

These must be present in any implementation for correctness. They are not deferrable. Code comments reference them by number ("Contract 7"); the numbers are stable.

| # | Contract | Severity | Notes |
|---|---|---|---|
| 1 | `UnresolvedBuffer` capped (default 10k entries) with LRU eviction | High | Without a cap, a Kafka outage grows the buffer unboundedly until OOM |
| 2 | `Collect()` holds RLock around the entire `GlobalState` iteration | High | Prometheus scrape races the scraper writer; without RLock the Go runtime fatals on concurrent map iteration |
| 3 | `*TenantMeta` updates always replace the pointer; never mutate fields in-place | High | Multiple MACs share one pointer ([data-structures.md](./data-structures.md#userspace-structures)). In-place mutation creates torn reads on the hot path |
| 4 | Boot ordering ([boot-and-recovery.md](./boot-and-recovery.md)) enforced with explicit sync points: steps 1–5 run straight-line in `Bootstrap` (single goroutine, `boot.Sequencer` validating phase order), and every worker that mutates kernel or GlobalState state blocks on `Sequencer.Await(PhaseStateRestored)` before its first action — the ghost sweeper, Kafka consumer, and reconciler all do | High | Out-of-order startup silently produces permanently-misclassified flows. `Sequencer.Fail` releases awaiters on a failed boot so workers exit instead of hanging |
| 5 | u64 wraparound guard in delta math | Low | At 10 Gbps continuous, ~467 years to overflow — but the guard is one comparison, so add it |
| 6 | Lingering Ghost lifecycle ordering between kernel `mac_tenant_map` and userspace `ShardedMetadataMap` | High | Insertions go userspace→kernel; deletions are delayed 60s then go kernel→userspace ([data-structures.md](./data-structures.md#map-lifecycle-invariants)). Skipping the kernel-side delay silently breaks the ghost's purpose — dying FIN/RST packets mis-attribute to `unknown` |
| 7 | Exposed billing series are monotone within their layer's lifetime: any mutation that deletes or re-attributes a `GlobalState` flow row folds its total into the tenant-settled AND server-settled accumulators in the same critical section ([data-structures.md](./data-structures.md#settled-bytes)), snapshots (Collect, WAL) read all maps under one lock, series are restored cumulatively across restarts, a server-settled bucket is released only on Nova-list server death, and a tenant-settled bucket is released only on Keystone-list project death — folding into the total-settled absorber in the same critical section (`unknown` exempt), so the tenant tier never decreases while its project lives, the server tier never decreases while its server lives, and the total tier never decreases at all | High | Billing consumers bill by endpoint-sample subtraction ([billing.md](./billing.md)) and depend on monotone cumulative counters. Late-bound labels mean row-level append-only is NOT sufficient — deleting metadata re-buckets history, which is a series decrease. Any future eviction/retention feature must preserve the fold-forward property or version the consumption contract first |

## Deferred work

Explicitly out of scope for now — open by design, not oversight. Numbers are stable (chapters reference them as "deferred item N"); a shipped item keeps its row, marked as such, rather than renumbering the rest.

| # | Item | Notes |
|---|---|---|
| 1 | IPv6 zone resolution | All v6 unicast traffic currently classifies as ZONE_MISS (v6 multicast lands in the multicast zone). Retrofit path: add a second LPM trie keyed `(tenant_id, u8[16])` alongside the existing v4 trie; branch in `lookup_zone()` on `eth_proto`. The five-step cold-start algorithm is IP-version-agnostic — only insertion code changes. Effort: small, low risk |
| 2 | Traditional Neutron (OVS-agent + L3-agent + qrouter namespaces, with or without DVR) | Tested OVN deployments (single-node and 3-node HA) run OpenStack Yoga with OVN ML2 — verified empirically. Traditional Neutron is therefore out of scope. If a future deployment requires it, the cold-start algorithm needs a "DVR per-host MAC enumeration" step reinstated (using the `dvr-mac-addresses` Neutron extension); see git history of the design doc for the removed text. Effort: small |
| 3 | ~~Cross-goroutine boot sync barrier~~ — **shipped** | `boot.Sequencer.Await(Phase)` / `Fail(err)` exist and are exercised by the ghost sweeper, Kafka consumer, and reconciler (Contract 4). Row retained so item numbers stay stable |
| 4 | Static-route EXTERNAL-fallback counter (`lachesis_neutron_static_route_fallback_total{reason}`) | `resolveStaticRouteZone` (resolve.go) has six EXTERNAL fallback exits; three warn-log (cycle, MAX_HOPS, ambiguity), the others (anchor-subnet miss, port-at miss, unknown next-router device, unknown device-owner) return EXTERNAL silently. A per-`reason` counter would make the fallback rate visible on `/metrics`. Deferred until it can be validated against a real cluster's `/metrics` deltas — it touches billing-relevant route classification, so per the project's validate-before-billing-changes rule it should not ship on theory. Observability-only (counts existing EXTERNAL returns; changes no classification). Effort: small, low risk |
| 5 | Netlink attach-presence reconciler (level-triggered periodic resync) | A periodic sweep that lists interfaces matching the attach allowlist and re-attaches our TC filters where missing — the informer "periodic resync catches missed events" pattern. Safe by construction: `FilterReplace` is idempotent (the fixed `tcattach.FilterPriority` makes it so — at priority 0 the kernel would allocate a new chain per call and stack a duplicate filter), so the worst a bug does is re-attach something already attached. Covers NEWLINK events missed around the subscribe window, and the larger missed-event surface under churn: a NEWLINK dropped by netlink socket overflow during an event storm never reaches the subscriber at all. **Scheduled (no longer purely evidence-gated):** the original gate — watch `lachesis_tc_attach_failures_total` — is moot, because that counter is blind to the dominant risk. A dropped NEWLINK never calls `AttachLink`, so nothing increments; the failure counter only sees explicit attach errors, not the missed-event path. The real detector is therefore a *presence gauge* (allowlist-matching links present-but-unattached), landed first as its own slice, with the reconciler acting on it. Event storms (mass VM operations, HA failover rescheduling many ports) make the missed-event path realistic rather than hypothetical. Explicitly **not** a runtime zombie hunter — zombie *deletion* stays boot-only by design, because its safety depends on running before any attach (at that point every matching filter is an orphan by definition); a runtime deleter must distinguish live filters from orphans, and a bug there silently deletes live filters → billing undercount. The risk asymmetry rules it out. Effort: small, low risk |
| 6 | Workqueue-backed event handling for the netlink subscriber and Kafka updater | Reference: `k8s.io/client-go/util/workqueue` (dedup/coalescing + rate-limited retry with exponential backoff) — the standard informer → workqueue → reconciler triple. Earmarked for: (a) the netlink subscriber, if flapping interfaces produce event storms or transient attach failures need retry-with-backoff instead of a log line; (b) the Kafka updater, to coalesce rapid per-port update bursts and retry failed kernel-map writes. Not applicable to boot — the boot sequence stays straight-line code plus ordering barriers, matching how Kubernetes boots components (`WaitForCacheSync`, post-start hooks), with queues reserved for steady-state events. **Current direction:** the lighter, targeted measures land first — netlink transient-failure and missed-event recovery folds into the idempotent re-attach of item 5 (the reconciler *is* the retry), and the Kafka side is handled by a debounce window that coalesces bursts (backlog, gated on observed event volume) rather than a full queue. The workqueue stays the escalation if those prove insufficient — adopt then, not before |
| 7 | ~~Map pinning for zero-loss agent-crash recovery~~ — **shipped** | `loadCollection` pins the counter-bearing maps (`telemetry_map`, `telemetry_stats`) under `bpf.pin_path` and reuses a compatible pin on boot, so an agent crash (kernel intact) recovers with **zero loss** instead of the WAL-bounded ≤60s ([boot-and-recovery.md](./boot-and-recovery.md#agent-crash-process-killed-kernel-intact)). Boot ordering is a non-issue by construction — the Zombie Hunter deletes TC *filters*, and the bpffs pin holds the map alive independently. A stale pin whose sizing/type no longer matches the build is refused (`MapSpec.Compatible`), removed, and recreated fresh — never silently adopted. When pinning cannot be established, strict mode (the default) refuses to boot; `bpf.unsafe_allow_unpinned_maps=true` opts into unpinned operation with the ≤60s recovery. The `lachesis_bpf_maps_pinned` gauge surfaces the live mode. Row retained so item numbers stay stable |
| 8 | Trunk port (VLAN-aware VM) support — single 802.1Q parse | When `h_proto` is `0x8100`/`0x88A8`, parse one VLAN level: `bpf_skb_pull_data` for the 4 extra tag bytes, re-read the data pointers, dispatch on the inner ethertype, and offset the IP header by 4; also handle the offloaded-tag direction (`skb->vlan_present`, where the tag lives in skb metadata and the linear data already starts at the inner header). Blocked on a billing decision: whether `flow_key.eth_proto` records the inner or outer proto (and whether counted bytes include the 4 tag bytes) must be settled **before** WAL entries bake the key shape. Until then trunk deployments are detection-only — cold-start warn-log, `lachesis_neutron_trunk_subports` gauge, and the kernel skipped-ethertype counter; see [edge-cases.md](./edge-cases.md) Tier 1 row 3a. Effort: medium |
| 9 | Allowed-address-pairs MAC ingestion | `ListPorts` does not fetch a port's `allowed_address_pairs`, so a MAC a VM is *permitted* to source (a keepalived/VRRP virtual MAC, or an AAP entry with an explicit MAC) never enters `mac_tenant_map` and its bytes leak to `tenant_id="unknown"` ([edge-cases.md](./edge-cases.md) Tier 3 row 14b; the revenue-leak SLO in [billing.md](./billing.md)). Fix: add `allowed_address_pairs` to the port query and admit each pair's MAC against the owning port's tenant — userspace-then-kernel like any other insert. The default keepalived case (real port MACs via GARP) already classifies, so this targets vMAC-mode and explicit-MAC AAP deployments. Effort: small, low risk |
| 10 | Budget-derived `telemetry_map` sizing | `max_entries` is a compile-time constant (65,536) today, so the preallocated PERCPU footprint scales with host core count — ~200 MB on a 128-core host, 4× the 50 MB design budget. The design target is `max_entries = clamp(8192, 65536, budget / (16 + 24×N_CPU))` exposed as config (default budget 50 MB); see [performance.md](./performance.md). The `lachesis_bpf_map_max_entries` gauge already surfaces the effective size per host. Effort: small |
